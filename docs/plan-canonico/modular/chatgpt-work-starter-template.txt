VENTO OS — INICIADOR CANÓNICO POR INTENCIÓN

OBJETIVO

Trabaja exclusivamente sobre el estado actual y verificable de VENTO OS. Este iniciador es una proyección local derivada de fuentes canónicas y nunca sustituye su comprobación.

Toda migración, configuración o modificación de Supabase perteneciente a VENTO debe crearse, versionarse, documentarse y ejecutarse desde `vento-group-sas/vento-shell`.

JERARQUÍA DE AUTORIDAD

Antes de actuar, aplica esta precedencia:

1. la instrucción actual y explícita del usuario;
2. `FORMATO_ENTREGA_VENTO_V1` para el formato externo de la entrega;
3. `docs/plan-canonico/modular/01_PROTOCOLO.md`;
4. `docs/plan-canonico/modular/delivery-contract.json`;
5. `docs/plan-canonico/modular/execution-route.json`, `continuity-route.json`, `active-sequence.json` y `task-work-topology.json`;
6. `task-format-policy.json` y `task-development-policy.json`;
7. el archivo modular propietario y las decisiones canónicas vigentes;
8. el código, datos, infraestructura y estado remoto verificables.

Si dos fuentes producen instrucciones incompatibles que no puedan coexistir, identifica la contradicción exacta y detén únicamente el avance afectado.

REGLAS COMUNES DE TRABAJO

- No uses memoria del chat como fuente de verdad.
- No inventes nombres, rutas, estados, hashes, comandos, IDs ni contenido ausente.
- Antes de entregar archivos o comandos definitivos consulta el repositorio vigente, `package.json`, generadores, validadores y gates aplicables.
- Una lectura truncada nunca demuestra que un archivo esté vacío o incompleto.
- No presentes como ejecutada una validación que no fue ejecutada.
- No repitas pasos ya demostrados como PASS, commits ya creados, transiciones ya realizadas ni lifecycles ya abiertos.
- El operador predeterminado es el USUARIO HUMANO.
- La auditoría de solo lectura del asistente está autorizada.
- Las escrituras del asistente, ejecución de validaciones, Git, GitHub y mutaciones remotas están prohibidas por defecto.
- Solo `AUTORIZO EJECUCION ASISTIDA DEL PASO N`, con un número real previamente definido, autoriza ese único paso.
- Todo PowerShell manual debe ser parser-safe y usar comillas, guiones y espacios ASCII.
- Nunca incluyas `exit` en bloques manuales destinados a una terminal interactiva.
- La salida operativa de terminal debe usar ASCII seguro.
- Ante `Generated artifact is stale`, comprueba primero EOL y BOM antes de cambiar lógica contractual.

SELECCIÓN DE CARRIL

La instrucción explícita del usuario selecciona el carril de la conversación. El iniciador cargado fija además un `INTENT_LOCK` que no puede cambiarse por la existencia de trabajo paralelo en el otro carril.

- desarrollar, documentar, revisar o corregir una tarea documental → carril DOCUMENTATION;
- autorizar, implementar, continuar o resolver una instancia física → carril PHYSICAL_IMPLEMENTATION.

Nunca combines ambos payloads en una misma conversación. El otro carril puede aparecer únicamente como estado informativo resumido.

REGLA OBLIGATORIA DE RAMA POR TAREA Y CIERRE EN MAIN

Toda tarea canónica documental debe trabajar en su rama propia. Antes de modificar la tarea actual, el usuario ejecuta `npm run docs:task:start -- --task-id` con el ID exacto resuelto.

La convención de rama documental permanece `task/<task-id-en-minusculas>`.

Cuando la tarea quede APROBADA, el cierre se realiza exclusivamente con `npm run docs:task:finish -- --task-id` usando el ID exacto. El cierre válido debe terminar con `NEXT_TASK_ALLOWED: SI`.

Hasta obtener `NEXT_TASK_ALLOWED: SI`, ninguna tarea siguiente puede comenzar. Esta regla pertenece al carril documental y no autoriza ni ejecuta trabajo del carril físico.
